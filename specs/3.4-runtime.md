# 3.4 Runtime 引擎

**Scope**：`agent/features/runtime/**`——Agent 主循环、tool 执行编排、token budget、对话压缩（compact）、Usage 事实关联、slash 命令系统。
**主触发**：改 `agent/features/runtime/**`。
**次触发**：改暂停 / 恢复 / 重试 / 取消 / 超时 / terminate / 终态投影；改 Usage 事实关联；新增 slash 命令。
**配套**：Tool Published Language、Catalog/Execution 端口与 MCP 主体在 `specs/3.5-3.5-tools.md §3.5`；provider 调用在 `specs/3.6-3.6-provider.md §3.6`。

## 3.4.1 配置应用边界

- Runtime **MUST** 在接纳真实用户输入、创建 Main Run 前调用 `ConfigReader::refresh_if_sources_changed()`；同一次 Run 内 **NEVER** 再 refresh。
- Main Run 与每个新 Subagent Run **MUST** 捕获一个 `RunConfigSnapshot`；provider binding、WebSearch 的 HTTP `User-Agent`、`allow_all`、hooks、language、timeout 与 context size 随该 Run 固定。
- Hook capability 由 `RunSpec::hook_binding()` 选择：Main 的 Full 与 Sub 的 BoundaryOnly 都使用本 Run frozen snapshot 构造 Dispatcher；BoundaryOnly **MUST** 按 Hook-owned metadata 转发所有 Boundary point（含 Stop），过滤 Tool/Notification point，**NEVER** 使用硬编码 allow-list 或空 Hook 实现绕过 shared Stop path。
- `api.user_agent` 属于 `Run` scope：Provider 与 WebSearch 在下一 Run 使用冻结快照；当前 Run 不变。
- Run Step 只从所属 `RunConfigSnapshot` 构造 `ContextRequest.config_snapshot`，**NEVER** 读取 `ConfigReader` / `ConfigQuery` 或配置文件。
- `SessionRestartRequired` scope 仅标记 pending session revision；当前 TUI/logger/MCP/storage 基础设施保持不变，成功 session resume 后清除 pending 标记。

## 3.4.2 会话历史唯一真相

- **MUST** 会话历史唯一可变真相属于 Context Management 的 `CanonicalSession` backing。
- **MUST** Runtime 每个 Run 用显式 Step message ownership 记录当前 Run/RunStep 的消息投影；**NEVER** 通过消息位置、长度、历史数量或索引推断归属。历史通过 `ContextPort::build_window` 读取，finalized Step 通过 `append_and_persist` 提交。
- **NEVER** Runtime 生产代码引用 `context::session::*`、`ChatChain` / `ChatSegment`，或恢复 `current_chain` / `frozen_chats` / `active_summary` 第二 backing。
- **NEVER** 恢复 `save_chain`、loop-exit auto-save 或 Runtime 自写 Session 文件；持久化由 Context 复用 Storage AtomicBlob。
- **MUST** `ChatRequest` 只传增量 `user_input`，**NEVER** 传全量消息历史。
- **MUST** idle `/compact`、reset 与自动 compact 经 ContextPort；启动 resume 与运行期 `/resume` 经同一 `MainSessionWiring::resume_session` 协调器。

## 3.4.3 Tool 执行编排

- 执行流程：LLM 返回 tool_use → Runtime 取得本次 Scope/Profile 的 Catalog snapshot → Policy/Hook/并发/timeout 编排 → 经 `ToolExecutionPort` 执行 → 结果注入回消息。
- Main/Sub Runtime 只持 `Arc<dyn ToolCatalogPort>` / `Arc<dyn ToolExecutionPort>` 与 Published Language，不持 `ToolRegistry`、不取得或调用 `Tool` 实例。生产装配入口在 `application/client/from_args.rs`，Tools 私有 backing 与双 adapter factory 见 `specs/3.5-3.5-tools.md §3.5`。
- Catalog 提供 schema/并发/timeout 描述；Execution 复验存在性、Scope/Profile、schema 后调用 Tool。schema 所有权归 Tools，Runtime 的 `application/agent/input_validation.rs` 仅为兼容 re-export / phase peel。
- ordinary 与 streaming Tool 执行 **MUST** 使用同一 `ToolDescriptor.concurrency` 语义：parallel-safe 调用 MAY 并发；sequential-only 调用 MUST 按 Provider `ToolCallCompleted` 的提交顺序严格 FIFO，前一调用完成执行、cleanup、terminal receipt 与 ToolResult 发布后才可启动后一调用。ToolCall ID 仅用于 identity/关联，NEVER 用 UUID 或字符串排序替代提交顺序。**例外（#252 后台任务模型，仅 Main Run）**：前序调用超阈值自动转后台后，其「前台契约」视为已履行——占位 ToolResult 已发布、receipt 进入 `Backgrounded`、cleanup 延期至终态——同轮后续 sequential-only 调用 MAY 启动，启动顺序仍严格 FIFO；Sub Run（派生装配）**MUST** 显式禁用自动转后台（子代理收口后占位无处回注、通知无法语义路由）。
- Runtime 自行持有 `WorkspacePersist`、并发 semaphore、timeout、Policy/Hook、取消实现与 interaction waiter；这些 **NEVER** 流入 Tools domain。`WorkspaceViews` 只在 Runtime adapter 转成窄 live capabilities，`ExecutionScope` 只传纯值快照。
- Tools 返回 typed `ToolSuspension`；Runtime 映射为交互值并拥有 request identity、等待、continuation、resume 与取消。旧 Runtime-owned AskUser oneshot 仅为兼容路径，不得据此复制第二套状态机。
- 唯一稳定 `Skill` Tool 经正式 Tool Catalog/Execution 发布并执行；Main/Sub Context 只注入 metadata directory，正文由 `SkillLoadPort` 在调用时按 identity 加载。Runtime 只接纳 typed `SkillRequest` 并投影模型意图，**NEVER** 读取 Skill 文件。
- Runtime **MUST** 为 Skill 去重装配稳定主体作用域：Main Session 的所有 Main Run 共用 `SkillLoadScope::Main`；每个 Sub-agent instance 创建一次独立 scope 并在其全部 Step/Tool round 中复用。Sub RuntimeContext 继承父级 Context-owned `SkillLoadStatePort` 与 Main Session identity，**NEVER** 使用 `run_id` 或 Sub 的 isolated Session 作为 durable 去重真相。

## 3.4.4 取消、超时与终态协议

- **MUST** 将取消视为包含请求受理、执行资源收敛、terminal receipt 持久化、Step finalize 和权威终态投影的协议，**NEVER** 简化为一次 token 操作。
- **NEVER** 通过 drop Tool future 假定外部副作用已停止。Runtime 收到取消后 **MUST** 等待 Tool cleanup 与 terminal receipt 持久化完成，再 finalize Step。
- 外层 timer 触发不自动构成硬超时。阻塞型 Tool **MUST** 在 blocking 边界执行并合作式检查取消；外部进程 Tool **MUST** 终止进程树、等待宽限、必要时强杀并回收。
- timeout、cancel、cleanup 与 terminal receipt **MUST** 由 Runtime 的统一监督入口编排；**NEVER** 在 Main/Sub、普通 Tool、Agent 或 approval continuation 中复制第二套机制。
- **后台任务模型（#252，仅 Main Run）**：tool call 派发即登记后台任务记录，超过阈值（`runtime.tool_background_threshold_secs`，默认 10（PR3 起交付完成开启；`0`=显式禁用）；随 `RunConfigSnapshot` 冻结）自动转后台——占位 tool_result 立即发布、receipt 推进 `Backgrounded` 中间态、**terminal 仍推迟到真实完成时写入**、转后台时三重 deadline 最早值拍快照由后台驱动继续生效。转后台后任务脱离 CancelStep 与 Run cancellation 管辖（step 已收口），停止仅经 `background_tasks` 工具；唯一取消源为 deadline 快照。快路径（阈值内完成）行为与现状一致；Sub Run 禁用（见 3.4.3 例外）。完成通知：有 active Run 经 Reminder 管线注入后续 step（`reminder_handle_event` → OnEvent source build（take 语义，每条完成事实只通知一次）），无 active Run 经 Wakeup Run 回注（`WakeupMailbox` 信号驱动 idle select，wakeup Run 启动时显式触发同一事件注入；授权来源 = agent 发起转后台，与 `continuation_authorization` 独立通道）。设计真相源 `docs/design/02-modules/runtime/09-background-tasks.md`。
- **MUST** 区分 Runtime 生命周期状态与业务终态。**Runtime 生命周期完成不等于业务成功**；内部 `Completed` 若包含取消、失败、终止、超时或其他非成功原因，出站事件 **MUST** 保留真实用户语义，**NEVER** 投影为成功。
- Runtime 是用户可见终态的唯一真相源。`RunStepCancelled` 等是生命周期观测事件；`Cancelled`、`DoneWithDuration`、失败/终止事件是权威业务终态。SDK/TUI **NEVER** 根据 identity 或事件顺序重新实现状态机。
- 一个 run step **MUST** 只发布一个用户可见终态；成功、取消、失败、终止、超时互斥，**NEVER** 同时发布冲突终态。
- 只有确认完成资源收敛的取消才能投影为已取消；`CancellationUnconfirmed` **MUST** 保持不确定语义，**NEVER** 伪装成取消成功或业务成功。
- cancel 的语义是「cancel 当前执行单元，进入 drain and settle」，**NEVER** 是 cancel run：TUI Esc / Ctrl-C 统一经无 identity 的 `AgentClient::cancel_current_run`（registry `cancel_current_main` 裁决唯一当前 Main Run）——有 active step 走 CancelStep 协议；Manual Reflection Run 无 RunStep（执行体由 root token 承载），按 `RunIntent` 只取消执行体 token、由执行体自行 `Cancelled` 收口，**NEVER** 置 `Terminate` control；Conversation 的 step 间隙无执行单元可 cancel，返回 `NoActiveStep`。terminate 语义只属于 idle 双击 Ctrl+C 的退出路径。用户取消的 Run 收口终态 **MUST** 投影为 `Terminated(UserExit)`（settle 投影），**NEVER** 伪装成 `SessionShutdown`（会话关闭）；`terminate_interrupted_run` 的终止 reason 由调用点按中断来源显式给出。实时与 Resume **MUST** 对同一持久化事实投影等价业务语义，并保留终态原因、耗时及用户可见结果。
- busy 期间 `/reflect-now` **MUST** 丢弃并提示、**NEVER** 排队执行；丢弃点 **MUST** 位于 Runtime 侧（Run 收尾回流 pending buffer 处与 gate 消费 pending buffer 前，共用 `input_gate::drop_queued_reflect_now`），**NEVER** 由 TUI 侧自行判断。

## 3.4.5 token budget / 压缩 / Usage

- token 估算由 Context BC 的 `context::api::compact::estimate_tokens` 提供，Runtime 在 `application/{agent,chat}` 编排中消费。
- Reminder 统一管线（真相源 `docs/design/02-modules/context-management/07-reminder-pipeline.md`）：Runtime 在 Run 装配期实现 `ReminderSource`（数据获取、启动期事实冻结）并经 `ContextPort::create_reminder_pipeline` 注册；Context 独占注入决策（per-kind policy：refresh 触发 / placement / dedup+priority+预算 / compact 处置）、统一 envelope 渲染与最终窗口注入。Run 结束 **MUST** 经 `drop_reminder_pipeline` 销毁句柄。canonical 落盘采用**显式落盘**语义（#1848）：尾部注入类（TailUserMessage）reminder 在 step 收口随 `append_and_persist` 提交 canonical（Context 内部 flush 待落盘清单并前置到提交消息头部，canonical 顺序为 user 输入 → reminder → assistant/tool 消息），使注入轮后的请求前缀逐 token 稳定（prompt cache 命中到最新 user 输入，断点仅在最新注入处）；SystemTail 类不落盘（system prefix 本来稳定）。落盘消息带统一 envelope（kind/version/at/seq），可识别、随 compact 清理；SDK/TUI 事件流零影响（持久化 JSON 含 reminder 消息属预期，resume 历史经 envelope 剥离展示）。重试路径 fingerprint 幂等早退，NEVER 重复插入。
- Reminder 按 per-kind policy 注入（不再「每 Run 至多一次」）：TaskProgress 为 `OnStepInterval` 周期重注入（`run_started` 以 step=0 提供首次注入；间隔内 fingerprint 去重，无变化时段同内容不重复注入）；guidance / model mismatch 为 Run 级恒定 `SystemTail`；memory 更新为 Run 启动事实。auto-compact `Committed` 后按 per-kind compact 处置重开（Rebuild / Reinstate / Drop）并作废注入指纹。Runtime **NEVER** 在 `ContextWindow → InvocationRequest` 映射后追加、插入或重写 Provider-visible message；Main 与 Sub 的所有 Provider-visible 内容 **MUST** 由 `ContextPort::build_window` 唯一生成。动态 refresh（OnStepInterval / OnEvent）的 kind 强制 `TailUserMessage`（缓存不变量，注册期校验拒绝违规 source）；#1458 的 TaskUpdate 摘要路径保持退役，不恢复。新增 reminder kind 只实现 source + policy 声明并注册，**NEVER** 触碰队列 / 注入 / 渲染分发代码。
- **显式例外（#1537）**：auto-compact 与 idle `/compact` 从 Runtime 的 `TaskAccess` 冻结单一 typed `CompactTaskSnapshot`，通过 `CompactRequest.task_snapshot` / `ManualCompactRequest.task_snapshot` 传给 Context。Context 在 Rust-owned Reduce 中只用 active batch、唯一 in-progress task 和同 aggregate revision 协调陈旧 working set 与唯一 Next action；pending task 与 companion 展示做确定性去重。main-user objective 保持其更高 authority，Task snapshot **NEVER** 成为用户授权来源，也 **NEVER** 修改 immutable constraints、prohibited actions 或 continuation status/reason。`## Current Task State` 仍是九分区之外的非权威 companion，但 **MUST** 由同一 typed snapshot 确定性渲染，连续 compact 丢弃旧 companion，不得解析 Markdown 反向构造状态，也不得送入 LLM。auto-compact 成功后 reminder 按 per-kind compact 处置重开（由 Context 在 `compact` 的 `Committed` 分支内部对接），使后续请求能反映压缩后的最新 Task 状态。
- **SHOULD** 修改涉及暂停 / 恢复 / 重试逻辑时同步检查 Context token estimation 调用点。
- Runtime **MUST** 只在成功 logical Model Invocation terminal 构造关联 `UsageRecord`，并经 session-scoped `UsageSink::try_record` 非阻塞发送；失败、取消、未报告 usage 不写，retry/fallback 不按网络 attempt 重复记账。
- Runtime **NEVER** 定义 Pricing、计算 Cost、发布 Cost DTO/event，或读写 `cost_history.json`。Cost/Pricing 属 Audit Future 能力，启用前 **MUST** 另行批准 Published Language、定价来源与迁移语义。
- `/cost` 仅作为历史命令名兼容映射到当前进程内 token Usage 展示；**NEVER** 声称或伪造金额。

## 3.4.6 slash 命令系统

- slash 命令的 SDK/TUI 入站路由属于 `application/client`；具体命令能力由对应 Feature 的 Published Language / Tool 提供。
- Command Published Language 与双端口由 Tools 独占，SDK 直接 re-export，Composition 向 TUI/no-TUI 注入同一 Catalog/Router；Runtime `PendingCommand` 仅作为目标 BC handler adapter，**NEVER** 再解析 slash 名称、alias 或参数 schema。
- Runtime 内不维护固定层命令注册表；新增命令必须先进入 Tools-owned Descriptor/Catalog，并由实际 owner 提供 handler，**NEVER** 恢复 SDK/TUI/Runtime 静态清单。
- 命令在 TUI 的展示样式见 `specs/3.3-3.3-tui-cli.md §3.3`。
