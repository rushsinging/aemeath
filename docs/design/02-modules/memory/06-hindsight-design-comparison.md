# Memory · Hindsight 对照设计

> 层级：02-modules / memory（模块战术设计）
> 状态：Target（目标设计）｜Milestone：v0.1.0
> 本文以 [05-hindsight-research.md](05-hindsight-research.md) 的调研事实为基础，逐项对照 aemeath Memory BC 现状，给出采纳判断、建议设计与风险。**只定义设计方向，不含实施排期**。

## 1. 对照方法与总结论

### 1.1 对照维度

每项按五段展开：**外部做法 → 本项目现状 → 差距 → 建议设计 → 成本与风险**，并给出明确的采纳结论。

### 1.2 一项必须先澄清的术语错位

Hindsight 的"层"与本项目的 `MemoryLayer` **不是同一个维度**，混淆会导致错误设计：

| 概念 | Hindsight | aemeath |
|---|---|---|
| 层的含义 | **认知梯度**（提炼深度：原始事实 → 观察 → 心智模型） | **作用域**（`Global` 跨项目 / `Project` 项目内） |
| 层是否可变 | 事实随巩固升级为观察（跨层演进） | 创建后不可变（不变量 M2） |
| 层数 | 4 | 2 |

**结论**：本项目的 `MemoryLayer` 与 Hindsight 的认知梯度**正交**。引入后者不改变 `MemoryLayer` 语义，也不与 M2 不变量冲突 —— 二者应作为两个独立维度共存。

### 1.3 四项不是独立特性，而是一条依赖链

这是本次对照最重要的结构性结论：

```text
项 4（取代关系）─┐
                ├─→ 项 2（证据指针）─→ 项 3（巩固水位）─→ 项 1（归纳层）
项 4 独立可做 ──┘
```

- **项 4 可独立落地**：它只要求 `MemoryEntry` 能表达"记忆 A 被记忆 B 取代"，不依赖其他三项。
- **项 2 与项 4 同层**：两者都是"记忆之间的关系表达能力"，可共用同一组字段与同一套不变量。
- **项 3 是项 1 的前置**：没有"哪些记忆已被归纳"的水位，归纳层无法增量推进，只能全量重算。
- **项 1 是终点且成本最高**：它把 Memory BC 从纯数据域升级为带推导链的域，前置依赖未就位时强行引入会产生无法维护的中间态。

**因此不建议把四项作为四个并行的独立特性推进**，应按依赖链顺序评估：先解决"记忆之间的关系表达"，再解决"归纳的进度追踪"，最后才引入归纳层本身。

## 2. 项 1：四层认知梯度（含零 LLM 读取层）

### 2.1 外部做法

源文档 → 原始事实 → 观察 → 心智模型四层，每层向"读取更便宜"演进。终态的心智模型读取为纯数据库查询（预生成落库 + 数据水位门控），零检索、零 LLM 调用。

### 2.2 本项目现状

- 只有**一个记忆层**：`MemoryEntry`。`MemoryLayer` 是作用域维度（见 §1.2），不构成梯度。
- `MemoryCategory`（`Fact` / `Decision` / `Preference` / `Pattern` / `Pitfall`）按设计**不驱动行为策略**，仅是分类标签与检索匹配维度。
- Reflection 的 `MemorySuggestion` 经 apply 后**直接成为 `MemoryEntry`** —— 链路是"对话 → 记忆"，中间没有归纳层。
- 自动注入 `<memory-context>` **本身已是零 LLM 读取**（`retrieve_for_inject` 是纯函数查询，不 touch、不落盘）。但注入内容是原始条目，且**没有自动重写机制**。

### 2.3 差距

| Hindsight 层 | 本项目对应物 | 判定 |
|---|---|---|
| 源文档 | Session 消息（CanonicalSession） | 已有，但不属于 Memory BC |
| 原始事实 | `MemoryEntry` | 已有 |
| 观察（跨条目归纳） | **无** | **真实缺口** |
| 心智模型（自动重写的常驻答案） | AGENTS.md 等人工维护的注入内容 | **部分具备**：读取路径已零 LLM，但内容需人工维护 |

关键判断：**本项目的"零 LLM 读取"能力已经具备**（注入机制即是），缺的是"答案由系统自动重写"这一属性。

### 2.4 建议设计

**部分采纳，且分层对待**：

1. **不引入完整四层**。本项目的记忆规模（`max_entries` 量级）远小于外部系统的百万行量级，四层梯度的收益主要来自规模效应。
2. **归纳层（观察）**只有在项 2、项 3 落地后才具备可维护性 —— 否则观察既无证据指针、也无增量进度，任何一次源记忆变更都会导致观察失效且无法重算。
3. **零 LLM 读取层**建议以轻量形式评估：把"常驻问题"（如"本项目技术栈与约定是什么"）的答案作为**预生成文档**缓存，由 Reflection 或巩固流程刷新。若采纳，其读取路径可直接复用现有注入机制（`MemoryPort::retrieve_for_inject`），不需要新的检索能力。

### 2.5 成本与风险

| 风险 | 说明 |
|---|---|
| 复杂度跃迁 | Memory BC 从"数据域"变为"带推导链的域"，不变量、端口、错误语义全部上升一个量级 |
| LLM 成本 | 观察生成与刷新都是 LLM 调用；外部系统为此设计了水位门控、成本地板、失败熔断三层控制，本项目需同等控制才可控 |
| 中间态不可维护 | 只做归纳层而没做证据指针与水位，会产生"无法回答证据、无法增量重算"的观察 —— 比没有更糟 |
| 与现有 Category 的关系 | 观察是**跨类别**的归纳，不宜作为第 6 个 `MemoryCategory`；应作为独立的类型维度（与 `Category` 正交） |

**结论：暂不采纳完整梯度；归纳层列为依赖项 2、3 就绪后再评估的方向。零 LLM 读取层的自动重写建议单独评估收益。**

## 3. 项 2：证据链、证据计数与演变史

### 3.1 外部做法

- 观察持有 `source_memory_ids`（证据指针数组）+ `proof_count`（**去重后**计数）。
- 证据引文**不单独存储**，通过指针引用源记忆正文。
- 演变史存放于独立快照表（`observation_history`），每次改写追加一行 `previous_*` 快照。
- 时间边界在合并时**只增不减**（`LEAST` / `GREATEST`）。

### 3.2 本项目现状

- `confirmation_count: u32` 单调递增（不变量 M4）—— 是**计数**，不是证据。
- 写入去重：Jaccard ≥ `similarity_threshold`（默认 0.8）时合并，行为是"tags 取并集 + touch（递增确认计数）"。
- `archive` / `restore` 已存在：归档**不删除**条目，可被显式 `search` 检索（不变量 R2）。
- `outdated: bool` 不可逆（不变量 M5）。

### 3.3 差距

| 差距 | 具体表现 |
|---|---|
| **合并是信息销毁式的** | A 与 B 相似度超阈值合并后，被合并条目的正文不再出现在 active 集合中；仅 tags 并集与计数被保留。**无法回答"这条记忆吸收了哪些内容"** |
| 证据不可追溯 | 无法回答"这条决策的依据是什么"；`source` / `source_ref` 只记录来源类型（Llm / Hook / User），不记录具体证据条目 |
| 无法表达信念演变 | `outdated` 是二分且不可逆，不记录"被谁取代、以什么理由取代" |
| 计数语义模糊 | `confirmation_count` 混合了"重复写入"与"相似合并"两种来源，无法区分 |

### 3.4 建议设计

**部分采纳 —— 采纳证据指针，暂不引入独立演变史表**：

1. **`MemoryEntry` 增加证据指针字段**：记录被合并/被引用条目的 `MemoryId` 列表。由于合并后的原条目仍可通过 `archive` 保留，指针有真实指向，不会悬空。
2. **合并语义改为"保留 + 引用"**：合并时把被合并条目归档（而非静默丢弃），在新条目上记录证据指针。这与现有"归档不删除"原则一致，无需新的存储能力。
3. **暂不引入独立历史快照表**：本项目的 `archive` 已提供"历史版本可查"能力，新增快照表会与 archive 职责重叠。演变叙事建议先用正文文本表达（形如"先前采用 X，现已切换到 Y"），与项 4 的取代关系配合。
4. **拆分计数语义**：若采纳证据指针，需要明确 `confirmation_count` 是"重复写入次数"还是"合并吸收的条目数"，二者不应混用同一个字段。

### 3.5 成本与风险

| 风险 | 说明 |
|---|---|
| 归档体积增长 | 合并不再销毁信息 → archive 必然增长；现有淘汰策略面向 active，archive 的容量需要单独定义 |
| 指针一致性 | 需要不变量守护（证据指针必须指向同层、已归档或 active 的真实条目） |
| 序列化兼容 | 新增字段需保持向后兼容；现有设计已使用 serde alias 处理旧字段名，沿用该模式 |
| 与去重的交互 | 合并阈值不变，但合并动作的副作用变更（归档 + 记录指针），需回归覆盖 `write` 路径 |

**结论：采纳证据指针与"合并即归档"语义；暂不引入独立演变史表。**

## 4. 项 3：巩固水位记在最小单元

### 4.1 外部做法

- `consolidated_at` 记录在**单条记忆**上，而非 bank 级水位；崩溃只影响在途一条，已处理项不重跑。
- 失败标记 `consolidation_failed_at` 使失败可被 API 重试，不静默丢失。
- 数据库对账例程周期性扫描遗漏项，并排除已有在途任务的重复入队。
- 进度查询靠部分索引（`WHERE consolidated_at IS NULL AND fact_type IN (...)`）。

### 4.2 本项目现状

- 记忆 mutation 是即时写入：构造 candidate → Storage dataset transaction durable commit → 无失败发布。
- Reflection 的触发对象是**对话消息快照**，触发条件是 `interval_runs`（默认 10）计数，另有 PreCompact 与 Manual 来源。
- **没有任何"记忆条目是否已被处理"的进度字段**。

### 4.3 差距

两者的**驱动对象不同**：

| 系统 | 后台处理的对象 | 进度基准 |
|---|---|---|
| Hindsight | **记忆条目**（未被归纳的事实） | 单条记忆的 `consolidated_at` |
| aemeath | **对话消息**（快照） | Run 计数（`interval_runs`） |

差距有两处：
1. 若引入归纳层（项 1），必须知道"哪些记忆已被归纳"，否则每次只能全量重算。
2. 即使不引入归纳层，Reflection 的触发目前**不判断内容是否变化** —— 单纯按 Run 计数触发，可能在无新信息时仍然发起 LLM 调用。

### 4.4 建议设计

**条件采纳**：

1. **作为归纳层的前置条件**：若项 1 进入实施，`consolidated_at` 类水位是必需项，且必须记在**单条记忆**上（而非层或项目级）。
2. **独立价值有限但思路可迁移**：Reflection 触发可引入"内容水位"判定 —— 只有自上次反思以来存在新的可反思内容时才发起 LLM 调用。这可复用现有 `ReflectionRecord` 历史，无需新存储。
3. **命名对齐**：若引入，字段命名应与 `last_confirmed_at` / `created_at` 风格一致。

### 4.5 成本与风险

| 风险 | 说明 |
|---|---|
| 与现有触发模型冲突 | 现有 Reflection 是消息驱动、单槽异步、busy skip；引入记忆驱动水位是**第二套触发模型**，需明确二者关系（互补还是替代） |
| 无数据库优化可用 | 外部系统依赖部分索引与 PL/pgSQL 对账例程；本项目是 JSON 文件存储，对账需在应用层实现 |
| 水位的语义边界 | 必须明确水位是"最后一次成功归纳的时间"还是"已归纳到哪个版本"，混用会导致漏算 |

**结论：条件采纳 —— 作为归纳层前置必需；独立落地价值有限，但"内容水位门控 LLM 调用"的思路可独立评估。**

## 5. 项 4：矛盾用文本合成而非数值置信度

### 5.1 外部做法

- 信念矛盾时**改写文本并保留演变史**，而非调整数值置信度。
- 该系统的 `confidence_score` 列已被迁移删除（原仅用于已移除的事实类型），当前 schema 无任何数值置信度。
- 彻底被取代时才删除重建；prompt 明确要求"对删除极为保守"。
- "过期"是推导值：范围内存在未处理的更新时，相关归纳被视作 stale 并下钻验证。

### 5.2 本项目现状

- 相似（Jaccard ≥ 阈值）→ 合并；不相似 → 并存。
- Reflection 通过 `outdated_memories` 标记过期，标记**不可逆**（M5）。
- **没有矛盾检测**：两条语义相反的记忆（例如"用 JSON 文件存储"与"改用嵌入式数据库存储"）Jaccard 相似度低 → 判定为不同记忆 → **并存** → 自动注入时**同时进入上下文**，模型收到互相矛盾的信息。

### 5.3 差距

| 差距 | 严重性 |
|---|---|
| 无"取代"关系 | **高**：矛盾记忆可同时注入，直接影响模型行为 |
| `outdated` 不记录取代者 | 中：无法回答"这条为什么过期、被什么取代" |
| `outdated` 不可逆 | 中：误判无法回退，只能新增记忆纠正 |

**这是四项中确定性最高的缺陷** —— 它不依赖其他三项，且当前设计已具备修复所需的大部分机制（归档、Reflection apply、注入过滤）。

### 5.4 建议设计

**采纳**：

1. **引入取代关系字段**：`MemoryEntry` 记录"被哪条记忆取代"的关系（可选字段，形如 `superseded_by`）。被取代条目在注入时硬过滤，与 `outdated` 同为 eligibility 判定，但语义更精确（`outdated` = 不再适用；`superseded_by` = 明确被另一条替代）。
2. **Reflection 输出扩展**：现有 `outdated_memories: Vec<String>` 升级为携带因果的结构（旧记忆 id + 取代者内容或 id + 原因），使 apply 能建立取代链而非仅打标记。
3. **坚持不引入数值置信度**：与现有 `confirmation_count` 的计数语义保持一致，避免引入需要调参且难以审计的浮点数。矛盾表达交给正文文本与取代关系。
4. **保留 `outdated` 的不可逆语义**（M5 不变）：取代关系是**新增维度**，不替换 `outdated`；二者共存且语义分离。

### 5.5 成本与风险

| 风险 | 说明 |
|---|---|
| 取代链成环 | 需新增不变量：取代关系必须无环（可沿链上溯校验） |
| Reflection 输出兼容 | schema 变更需处理既往格式；建议以可选字段扩展而非替换 |
| 注入过滤变更 | `is_injection_eligible` 增加条件，需回归覆盖 M5 / R4 / R6 相关断言 |
| 归档条目被取代 | 被取代条目应进入 archive 而非删除，与现有"不删除"原则一致 |

**结论：采纳。这是四项中成本最低、收益最明确的一项，建议作为第一优先级。**

## 6. 采纳结论汇总

| 项 | 结论 | 前置依赖 | 优先级 |
|---|---|---|---|
| 项 4 取代关系 | **采纳** | 无 | **高**（可立即评估） |
| 项 2 证据指针 | **部分采纳**（指针 + 合并即归档；不做独立史表） | 与项 4 共用关系表达能力 | 中 |
| 项 3 巩固水位 | **条件采纳**（归纳层前置；思路可独立用于触发门控） | 无（作为项 1 前置） | 中 |
| 项 1 四层梯度 | **暂不采纳**完整梯度；归纳层待依赖就绪 | 项 2 + 项 3 | 低（长期方向） |

## 7. 与既有设计的对齐检查

| 既有决策 | 是否冲突 | 说明 |
|---|---|---|
| 双层记忆（`Global` / `Project`） | **不冲突** | 作用域维度与认知梯度正交（§1.2） |
| `Category` 不驱动行为策略 | **不冲突** | 观察若引入，应作为独立类型维度而非新 `Category` |
| 不变量 M1–M8 | **需扩展** | 取代关系需新增无环不变量；证据指针需新增一致性不变量；M5 语义不变 |
| 检索不变量 R1–R6 | **需扩展** | 被取代条目的注入过滤与结果表达需明确归属（对齐 R4 的"状态由 metadata 无损表达"） |
| Tier 1 BM25 为 v0.1.0 primary，Tier 2 embedding 属 Future | **不冲突但构成边界** | 外部系统的融合检索依赖向量与重排模型；本项目 Tier 2 未落地前，**不可照搬其检索架构** |
| `similarity_threshold` 仅用于写入去重 | **不冲突** | 取代关系判定不应复用该阈值（量纲不同），需独立策略 |
| `MemoryPort` 为 Memory-owned OHS | **需遵循** | 新增能力必须经 Port 发布，不得由消费方绕过 |
| Reflection 单槽异步、busy skip | **不冲突** | 取代关系由现有 apply 流程建立，不新增执行通道 |

## 9. 明确不采纳清单

以下外部设计经评估**不适用于本项目**，记录理由以避免后续重复评估：

| 设计 | 不采纳理由 |
|---|---|
| store-owned 存储抽象（流式写入会话协议） | 本项目单机 JSON 存储，无第三方后端替换需求；抽象成本远高于收益 |
| 双数据库后端全功能对等 | 专用后端代码量已超过主后端；不适用于单机场景 |
| 四臂并行检索 + RRF + cross-encoder 重排 | 依赖 embedding 与重排模型，与"Tier 1 零外部依赖"约束冲突；且本项目记忆规模无此需要 |
| 独立证据引文存储 | 通过指针引用源条目正文即可满足审计需求 |
| 数值置信度 | 需调参且难以审计；与计数语义冲突 |
| 多租户 schema 级隔离 | 单机工具场景不适用 |
| 数据模型的多后端谓词与索引分片策略 | 本项目无数据库层，相关优化不适用 |

## 10. 开放问题

1. **归纳层的真实需求边界**：本项目是否会出现"多条记忆需要跨条目归纳"的场景？若无，项 1 可长期不进实施。
2. **证据指针的归档容量策略**：合并即归档后 archive 会持续增长，是否需要独立的 archive 容量与淘汰定义？
3. **取代关系的判定归属**：由 Reflection 输出（LLM 判定）还是由写入时确定性规则判定？前者灵活但有误判成本，后者可控但覆盖有限。
4. **水位与现有触发模型的关系**：内容水位门控与 `interval_runs` 计数是互补还是替代？
5. **零 LLM 读取层的形态**：若引入，是作为 Memory BC 的新能力，还是复用 Context Management 的注入通道（不新增 Memory 端口）？
